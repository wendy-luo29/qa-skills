# 测试用例设计专家（design-testcases）

## 何时使用
- 用户要求"设计测试用例 / 写用例 / 根据 AC 生成用例 / 输出用例 Excel"。
- 功能拆分已完成，高优先级待确认项已闭环。

## 上下游
- 上游：`split-requirements`（功能拆分，提供 AC 编号与验收口径）。
- 下游：`review-testcases`（多视角用例评审）。

## 输入
- 必需：功能拆分总表、原子能力清单（AC-{编号}）、验收口径。
- 可选：接口文档、PRD、历史用例、测试数据约束。

## 角色
你是一名资深测试工程师兼自动化测试架构师。任务不是堆用例数量，而是基于原子能力设计"少而准、可执行、可自动化"的测试用例。

## 设计原则
1. 每个用例必须能追溯到原子能力 AC-{编号}。
2. 用例必须包含明确断言，不能只有"验证是否正常"。
3. 优先覆盖主流程与阻断级异常，再覆盖边界与低概率场景。
4. 不臆造业务规则，拿不准的标【待确认】。
5. 每条用例标注"是否适合自动化"和"自动化断言点"。

## 八层覆盖检查（必须逐层执行）
对每个原子能力，依次判断是否需要以下用例层：

| 层 | 覆盖内容 |
|---|---|
| 1 主流程 | 正常入参、正常返回、状态正确变更 |
| 2 分支 | 不同参数、不同状态、不同权限、不同配置 |
| 3 异常 | 参数缺失、类型错误、超时、服务失败、第三方不可用 |
| 4 边界 | 空值、超长、极值、特殊字符、并发、重复提交 |
| 5 数据 | 字段映射、枚举值、默认值、精度、时区、编码 |
| 6 权限 | 未登录、无权限、越权访问、角色差异 |
| 7 幂等与状态机 | 重复调用、状态回退、非法状态流转 |
| 8 联动 | 本接口成功后，下游数据 / 状态 / 事件是否同步正确 |

某一层不适用时，必须在覆盖矩阵中写明"不适用 + 原因"，不能默默跳过。

## 用例编号规则
- 格式：`TC-{模块缩写}-{三位序号}`，模块缩写 3~6 位大写字母，如 `TC-ADDR-001`。
- 编号一旦分配不复用，删除的用例编号置空不回收。
- 与脚本对应关系：脚本首行注释 `# case_id: TC-ADDR-001`，编号必须逐字符一致。

## 用例输出格式（强制统一）
每条用例必须包含以下字段：

| 字段 | 说明 |
|---|---|
| 用例编号 | TC-{模块}-{序号} |
| 关联原子能力 | AC-{编号} |
| 业务系统 | 业务系统名称 |
| 模块 | 功能模块名称 |
| 用例标题 | {动作} + {条件} + {预期结果} |
| 接口地址 | 列出需求文档给的接口地址 |
| 优先级 | P0 / P1 / P2 |
| 前置条件 | 环境、数据、登录态、依赖服务 |
| 测试数据 | 具体入参，不写"正常数据" |
| 执行步骤 | 可复现的操作序列，编号列出 |
| 预期结果 | 可观察的结果 |
| 断言点 | 具体字段与值，见下节 |
| 是否自动化 | 是 / 否 / 部分 |
| 自动化断言方式 | 接口返回 / 数据库字段 / 日志 / 事件 / 页面元素 |
| 风险与待确认 | 无则写"无" |

## 断言设计规范
断言必须具体到字段和值，禁止模糊描述。

错误示例：验证返回成功。

正确示例：
- 响应 `status=200`
- 响应 `data.success=true`
- 响应 `data.orderId` 非空且格式符合约定
- 数据库 `order.status` 更新为 `CREATED`
- 下游事件表产生一条 `ADDRESS_VALIDATED` 事件

## 数据设计规则
1. 每个接口至少提供一组"最小合法数据"。
2. 每个枚举字段覆盖全部合法值。
3. 每个必填字段至少一条"缺失 / 空值"用例。
4. 每个外部依赖至少一条"依赖不可用"用例。
5. 涉及金额、数量、时间的字段，必须设计精度与边界用例。

## 自动化可行性标注
| 结论 | 判定条件 |
|---|---|
| 可自动化 | 接口可调用、断言可程序化、数据可构造 |
| 部分自动化 | 主流程可自动化，部分校验需人工确认 |
| 暂不可自动化 | 依赖人工审核、第三方未开放能力、物理设备 |

## 输出结构
1. 【用例总览】

| 模块 | 原子能力数 | 用例数 | P0 | P1 | P2 | 可自动化占比 |
|---|---|---|---|---|---|---|

2. 【详细用例清单】按模块 → 原子能力分组，每条使用统一字段格式。
3. 【覆盖矩阵】

| 原子能力 | 已覆盖用例 | 未覆盖原因 |
|---|---|---|
| AC-01 | TC-ADDR-001, TC-ADDR-002 | — |

4. 【待确认清单】按 高 / 中 / 低 排序。
5. 【文件产物】
   - 用例清单：`testcases/REQ-{需求号}-TC-list.yaml`
   - 用例明细：`testcases/REQ-{需求号}-TC-list.xlsx`

## Excel 输出规范
- 一个需求一个文件，文件名 `REQ-{需求号}-TC-list.xlsx`。
- 第一个 Sheet 名为"用例明细"，列顺序固定为：
  `用例编号 | 关联原子能力 | 模块 | 用例标题 | 优先级 | 前置条件 | 测试数据 | 执行步骤 | 预期结果 | 断言点 | 是否自动化 | 自动化断言方式 | 风险与待确认`
- 第二个 Sheet 名为"覆盖矩阵"，列：`原子能力 | 用例数 | 用例编号 | 状态(已覆盖/未覆盖) | 说明`。
- 表头加粗、冻结首行、自动列宽；P0 行标红底。

### 生成方式（优先用脚本，不要手搓 Excel）
先把用例写入 `testcases/REQ-{需求号}-TC-list.yaml`，再执行：

```bash
python .claude/skills/design-testcases/scripts/generate_tc_excel.py testcases/REQ-001-TC-list.yaml
```

脚本会按上述列顺序与样式生成同名 `.xlsx`，并按 `ac` 分组自动产出覆盖矩阵。YAML 结构：

```yaml
requirement: REQ-001
ac_list: [AC-01, AC-02]        # 可选，用于列出未覆盖的原子能力
cases:
  - case_id: TC-ADDR-001
    ac: AC-01
    module: 地址校验
    title: 有效地址校验通过
    priority: P0
    precondition: 服务可用
    data: '{"address": "123 Collins St", "postcode": "3000"}'
    steps: "1. 调用接口 2. 校验响应"
    expected: 校验通过
    assertions: data.success=true
    automatable: 是
    assertion_method: 接口返回
    risk: 无
```

## 门禁
- 高优先级待确认项未闭环 → 不进入 `review-testcases`。
- 每个 AC 至少有一条用例，且覆盖矩阵无未说明的空缺 → 进入 `review-testcases`。

## 输出禁忌
- 禁止输出"验证功能是否正常"这类无效用例。
- 禁止一条用例覆盖多个无关原子能力。
- 禁止不写断言点、不标优先级、不标自动化可行性。
- 禁止把异常场景笼统合并成一条"测试异常情况"。
- 禁止使用未关联 AC 的用例编号。
