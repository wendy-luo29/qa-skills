# 测试用例设计方法参考

本文档是子 Agent 设计测试用例时的核心参考，综合运用多种方法最大化覆盖率。

---

## 1. 等价类划分（Equivalence Partitioning）

将输入域划分为若干等价类（合法 + 非法），每类取一个代表值。

**对每个输入参数，识别：**
- **有效等价类**（≥2个）：能被系统正常处理的值域
- **无效等价类**（≥3个）：系统应拒绝/报错的值域

**示例（limit 字段，整型，范围 1~100）：**

| 等价类 | 代表值 | 类型 |
|--------|--------|------|
| 正常范围 1~100 | 20, 50 | 有效 |
| 超出上限 >100 | 1000 | 无效 |
| 等于下限 1 | 1 | 有效（边界） |
| 等于上限 100 | 100 | 有效（边界） |
| 小于下限 <1 | 0, -1 | 无效 |
| 非整数类型 | "abc", null | 无效 |

---

## 2. 边界值分析（Boundary Value Analysis）

在等价类边界处取值，覆盖：`min`, `min+1`, `max-1`, `max`, `null/empty`

**字符串字段边界：**
- empty string `""`
- 单字符 `"a"`
- 最大长度（如255） → `"a"*255`
- 超最大长度 → `"a"*256`
- 含特殊字符 `"特殊!@#"`

**数值字段边界：**
- `0`, `1`, `max_int`, `-1`, `max+1`
- **小数精度边界**：按字段写入精度取 `上界-0.01` / `上界` / `上界+0.01`（重量、尺寸）；金额取 `0.001`
- **业务阈值边界**：需求文档或 description 里的「>120cm 不可发」同样按此方法取值，如 `119.99 / 120.00 / 120.01`，不能只测一个明显超限值
- **分段边界**：价卡、费率、阶梯折扣等分段点，段首段尾各取「恰好」与「超一个精度单位」，并断言命中不同段

**分页参数专项：**
- page=0（边界）、page=-1（无效）、page=99999（超大）
- limit=0（无效）、limit=1（最小）、limit=最大限制值

### 2.1 计费公式边界四步法（涉计费/费率必做）

计费类需求的边界往往**不在文档里**，而在费率表与公式结构里。按以下四步逐项抽取，每项至少 2 个数据点：

| 步骤 | 要回答的问题 | 取值方法 | 反例（本次踩坑） |
|---|---|---|---|
| 1 分段 | 价卡/阶梯有几段？段边界是闭还是开？ | 查 DB 费率表列全段起点终点；每段出「段起点-精度 / 段起点 / 段起点+精度」 | 只测了 1kg、3kg 段，漏了 5kg 段切换 |
| 2 取整 | 取整方向、单位、发生在匹配分段之前还是之后？ | 构造「跨档 0.01」的两个点：`6.00` 与 `6.01`，断言后者多一个计费单位 | 未测 6.00 与 6.01，取整方向错误无法暴露 |
| 3 累加单位 | 续重/递增是每 1kg、每 0.5kg 还是每档固定值？ | 取「1 个单位」与「2 个单位」两个计费重（如 6kg 与 7kg），断言两次增量相等且等于单价×(1+税率) | 只测 5kg→6kg，无法区分「每档固定」与「每 kg 累加」 |
| 4 取数维度 | 同重量在不同 zone / 承运商 / 仓库下金额是否不同？ | 同重量发往两个 zone、或两家承运商，断言各自命中自己的费率卡 | 只测了单 zone，per_kg 取错卡不会被发现 |

原则：**先查表、再抽取、最后写用例**。文档只给公式形态（fee + (w-5)×per_kg），具体分段与单价必须来自 DB 实测；文档与 DB 冲突时以文档为准设计断言，并把 DB 事实写入矩阵备查。

### 2.2 用例类型判定（避免比例漂移与统计失真）

| 类型 | 判定标准 | 示例 |
|---|---|---|
| 正向 | 合法输入、阈值之外的正常业务路径 | 7kg 续重正常计费、calcMode=1 正常计价 |
| 边界 | 取值在阈值或段边界 ±1 个精度内，目的是验证阈值行为（接受或拒绝均可） | 119.99/120.00/120.01、5.00 vs 5.001、6.00 vs 6.01、尺寸 0.01 通过 |
| 负向 | 明显非法输入：必填缺失、类型错误、负数、0 值、非法枚举、不存在的资源 | 尺寸 0、weight=-1、carrierIds 与策略同时为空、承运商不存在 |
| 安全 | 注入、越权、敏感信息泄露 | SQL/XSS 注入字符 |

约束：
- **一条用例只能有一个期望方向**，正负混写必须拆（如「尺寸 0 拒绝」与「尺寸 0.01 通过」是两条用例）。
- 0 / 负数属于非法值，归负向；等于 minimum 的合法值（如 0.01）归边界。
- 类型比例（正向≥40%、负向≥30%、边界≥20%、安全≥10%）只作**提示**；补用例只能来自约束缺口或维度缺口，**不得为凑比例新增用例**。

## 3. 结对思维 / Pairwise Testing

用于参数组合爆炸场景，确保每**两个参数**的所有取值组合至少被一个用例覆盖。

**步骤：**
1. 列出所有参数及其取值集合
2. 构建参数因子表
3. 使用正交表方法选取最少测试组合覆盖所有参数对

**示例（地址搜索 POST /address/search）：**

```
因子矩阵：
A: keyword   → [null, 有效, 注入]
B: limit     → [正常(20), 最小(1), 无效(0)]
C: page      → [正常(1), 第2页, 无效(-1)]
D: orders    → [null, ASC, DESC]
E: queries   → [null, 有效字段]

结对覆盖目标：
(A,B), (A,C), (A,D), (A,E)
(B,C), (B,D), (B,E)
(C,D), (C,E)
(D,E)
```

**贴标签方法**：每条用例备注中记录覆盖的参数对，如：
`notes: "Pairwise: A=有效,B=20,C=1,D=ASC,E=null"`

## 4. 场景法（Scenario-based Testing）

描述端到端业务场景，包含完整上下文。

**场景分类：**
- **主成功场景**：典型正向业务流程
- **备选场景**：正常但不典型的路径
- **异常场景**：预期内的错误处理
- **异常中断场景**：网络中断、超时等

**模板：**
```
前提：[初始状态]
when/时间：[触发条件]
步骤：[有序操作序列]
then/结果：[期望结果]
```

## 5. 错误猜测（Error Guessing）

基于经验主动猜测系统可能出现的错误。

**常见缺陷猜测点：**

| 场景 | 猜测的问题 |
|------|-----------|
| 字符串字段 | 未过滤 SQL 特殊字符（',";--） |
| 数值字段 | 未校验负数、零、超大值 |
| 分页参数 | page*size 溢出整型 |
| JSON Body | 缺少必填字段时返回 500 而非 400 |
| 空列表返回 | 返回 null 而非空数组 [] |
| 联合查询 | keyword 与 queries 同时传入产生逻辑冲突 |
| 排序字段 | 传入不存在的字段名、SQL 保留字 |
| 中文关键字 | 编码问题导致乱码或查不到 |

## 6. 数据库约束驱动的用例生成

从表结构中提取约束，自动生成对应负向用例。

| DB 约束 | 对应测试思路 |
|---------|------------|
| NOT NULL | 传 null/空 → 期望报错 |
| UNIQUE | 插入重复值 → 期望唯一键冲突错误 |
| VARCHAR(n) | 传超长字符串 → 期望截断或报错 |
| TINYINT(1) | 传 2/3/-1 → 期望报错 |
| ENUM('A','B') | 传 'C' → 期望报错 |
| FK 外键 | 传不存在的外键值 → 期望报错 |
| DEFAULT | 不传该字段 → 验证 DB 中使用了默认值 |

## 7. 安全测试用例设计

**针对每个字符串类型输入参数：**

| 类型 | 测试 payload | 期望行为 |
|------|-------------|---------|
| SQL 注入 | `' OR '1'='1' --` | 200空/400錯誤，不暴露DB信息 |
| SQL 注入 | `'; DROP TABLE users; --` | 同上 |
| XSS | `<script>alert(1)</script>` | 字段内容被转义或拒绝 |
| 路径穿越 | `../../../etc/passwd` | 400 或内容被过滤 |
| 超大载荷 | 10000 字符的字符串 | 400 或截断，不崩溃 |
| 空白字符 | `"   "` (仅空格) | 合理处理（视为空或报错） |
| Unicode | `\u0000`（null字节）| 400 或过滤 |

## 8. 八层覆盖检查（设计完成后必做审查）

对每个原子能力/API，逐层判断是否需要以下覆盖层。**不适用时必须写明原因，不能默默跳过。**

| 层 | 覆盖内容 | 设计要点 |
|---|---|---|
| 1 主流程 | 正常入参、正常返回、状态正确变更 | 每个 AC 至少 1 条 P0 正向 |
| 2 分支 | 不同参数、不同状态、不同权限、不同配置 | 枚举值全覆盖 |
| 3 异常 | 参数缺失、类型错误、超时、服务失败、第三方不可用 | 必填字段负向全覆盖 |
| 4 边界 | 空值、超长、极值、特殊字符、并发、重复提交 | 长度 N-1/N/N+1 |
| 5 数据 | 字段映射、枚举值、默认值、精度、时区、编码 | DB 约束驱动 |
| 6 权限 | 未登录、无权限、越权访问、角色差异 | 认证/授权/数据权限 |
| 7 幂等与状态机 | 重复调用、状态回退、非法状态流转 | 状态转换矩阵 |
| 8 联动 | 本接口成功后，下游数据/状态/事件是否同步正确 | 验证 SQL 跨表 |

## 9. 用例去重与裁剪规则（控制规模）

8 条规则对每个字段生成多条用例，容易爆炸。设计完成后必须执行去重与裁剪：

### 去重规则
- **相同 (api_url, test_item, test_data 摘要)** 的用例合并为一条
- 同一字段的多个边界用例（N-1/N/N+1）可合并为一条"边界值校验"用例，test_data 中列出 3 组数据（业务阈值的边界点不适用本条，见下文裁剪规则）
- 多个必填字段缺失的负向用例，可合并为"必填字段校验"用例（每条仍单独标注 test_item）

### 裁剪规则
- 每个 API 的 P0 用例 ≤ 5 条（只保留主流程 + 阻断异常）
- 每个 API 总用例数建议 ≤ 30 条，超出需说明理由
- 低概率边界（如 10000 字符超长、并发）降为 P3，可按需裁剪
- 相似字段（如同为 varchar(50) 的 name/description）的长度校验可抽样，不必每个字段都测 N±1
- **业务阈值**（箱规、重量上限、金额/费率分段）的边界点不得合并或抽样，必须逐点保留
- **正负混写不得合并**：同一字段「越界拒绝」与「边界通过」必须是两条用例，否则类型统计失真、失败时无法定位方向

### 优先级裁剪
- 主流程正向 → P0
- 必填缺失/类型错误/唯一冲突 → P1
- 长度边界/枚举非法值 → P2
- 安全注入/并发/极端值 → P3

## 覆盖率检查公式

```python
def check_coverage(cases):
    total = len(cases)
    dist = {t: sum(1 for c in cases if c.get('test_type') == t)
            for t in ['正向','负向','边界','安全','权限']}
    print(f"总用例: {total}")
    for t, n in dist.items():
        target = {'正向':0.4,'负向':0.3,'边界':0.2,'安全':0.1,'权限':0}.get(t, 0)
        status = "OK" if (total and n/total >= target) else "未达标"
        print(f"{status} {t}: {n}/{total} = {n/total*100:.0f}%")
```

**目标：主流程与关键异常 100% 覆盖；P0/P1 用例必须可自动化；每个 AC 至少有一条用例。**

> 类型比例仅作提示：补用例只能来自约束缺口或维度缺口，不得为凑比例新增无覆盖价值的用例。
