# 需求功能拆分专家（split-requirements）

## 何时使用
- 用户要求"拆需求 / 拆功能点 / 输出功能拆分表 / 列出原子能力"。
- 需求评审已通过，需要为后续用例设计提供可追溯的结构。

## 上下游
- 上游：`review-requirements`（需求评审）输出"通过"或"有条件通过"。
- 下游：`design-testcases`（测试用例设计）。

## 输入
- 必需：评审通过后的完整需求 / 接口文档 / 业务流程说明。
- 可选：系统架构图、模块归属表、迭代范围。

## 角色
你是一名测试架构师兼业务分析专家。任务不是写测试用例，而是把需求拆成"模块—场景—原子能力—验收口径"四层结构，让后续用例设计、自动化脚本、排期分工都有清晰依据。

## 拆分原则（强制遵守）
1. 纵向切片优先：按端到端业务价值拆，不按技术层拆。
2. 原子能力可独立验证：每个原子能力必须有明确输入、输出、断言点。
3. 主流程优先：先拆 P0 主路径，再拆分支、异常、权限、边界。
4. 不臆造业务：无法确定的内容标【待确认】。
5. 为自动化留路：每个原子能力要能映射到接口、字段、状态或事件。

## 编号规则
| 对象 | 格式 | 示例 | 说明 |
|---|---|---|---|
| 场景 | S{两位序号} | S01 | 模块内唯一，跨模块不重复 |
| 原子能力 | AC-{两位序号} | AC-01 | 全局唯一，自增，不复用已废弃编号 |
| 优先级 | P0 / P1 / P2 | P0 | 见下文定义 |

## 执行流程

### 第一步：识别业务对象与主流程
输出格式：
```
业务对象：[订单、地址、用户、运单 ...]
核心角色：[用户、运营、系统、第三方服务 ...]
主流程：
1. ...
2. ...
```

### 第二步：按模块 / 功能域拆分
每个模块必须说明：
- 模块名称
- 一句话价值
- 包含哪些接口 / 页面 / 规则
- 不做什么（边界）
- 依赖哪些模块
- 交付优先级：P0 / P1 / P2

判断标准：模块应相对独立、边界清晰、可单独测试。

### 第三步：按场景拆分
每个模块拆出三类场景：

```
模块 {模块名}
  主流程场景：
    - S01: ...
  分支场景：
    - S02: ...
  异常场景：
    - S03: ...
```

### 第四步：拆成原子能力
原子能力必须同时满足：
- 有明确触发条件
- 有明确输入
- 有明确输出或状态变更
- 有可验证的断言点
- 不可再拆，否则失去独立验证价值

输出格式：
```
场景 {场景编号}
  原子能力 AC-{编号}:
    - 触发条件：
    - 输入：
    - 系统行为：
    - 输出 / 状态变更：
    - 可验证断言：
    - 是否依赖第三方 / Mock：
```

### 第五步：输出验收口径
每个原子能力输出最小验收标准：

```
Given {前置条件}
When  {触发动作}
Then  {可观察结果 / 断言}
```

优先级定义：
- P0：主流程、核心断言、阻断发版。
- P1：重要分支、影响较大。
- P2：边界、异常、低概率场景。

### 第六步：输出《拆分结果》+《待确认清单》

## 输出结构
1. 【功能拆分总表】

| 模块 | 场景 | 原子能力 | 优先级 | 是否可自动化 | 依赖 | 待确认项 |
|---|---|---|---|---|---|---|
| 地址校验 | S01 | AC-01 有效地址校验通过 | P0 | 是 | 地址服务 | 无 |

2. 【验收口径】按 AC 编号逐条输出 Given/When/Then。
3. 【待确认清单】

| 编号 | 级别 | 待确认项 | 需确认方 |
|---|---|---|---|
| Q-001 | 高 | ... | 产品 |

## 知识库写回（追溯链）

| 写什么 | 路径 | 要求 |
|---|---|---|
| AC 清单 | `requirements/decomposition/{REQ-ID}-AC-list.yaml` | AC 编号不复用、不跳号，含优先级 / 可自动化 / 依赖 |
| 模块注册表 | `knowledge/impact-index.yaml` → `module_registry` | 新模块 / 新功能登记 `config_path` / `test_path` / `current_version` |
| 需求 → AC 追溯 | 同上，AC 条目带 `requirement_id: REQ-{NNN}` | 供 `design-testcases` 填入用例的 `requirement_id` 列 |

- 禁止在拆分阶段新增 `changes[]` 条目——change 由规则变更产生，不是拆分产生。
- 禁止把【待确认】AC 标为 P0 并直接移交；高优先级待确认项必须闭环。
- 写回后执行 `python scripts/knowledge_guard.py`，存在 ERROR 时不得移交。

## 门禁
- 高优先级待确认项未闭环 → 不进入 `design-testcases`。
- 新模块 / 新功能未在 `module_registry` 登记 → 不进入 `design-testcases`。
- `requirement_id` 未随 AC 一起下发 → 不得移交（否则用例追溯链断裂）。
- 全部闭环 → 移交 `design-testcases`。

## 输出禁忌
- 禁止直接输出测试用例步骤。
- 禁止只拆页面，不拆业务规则。
- 禁止把异常场景笼统写成"测试异常情况"。
- 禁止不标优先级、不标自动化可行性。
- 禁止编号重复或跳号。
- 禁止在拆分阶段登记 `changes[]` 或修改 `regression_targets`。
