# 测试全流程编排（test-workflow）

## 何时使用
- 用户给出一份需求 / 接口文档，希望从零走完整条测试链路。
- 用户不确定当前该用哪个 Skill，或要求"按流程来"。
- 需要跨阶段追踪待确认项与产物。

## 流程总览

| 步骤 | Skill | 主要输入 | 产出 | 门禁放行条件 |
|---|---|---|---|---|
| 1 | `requirement-enrichment` | PRD / 接口文档 | 完善后的完整需求、待确认清单 | 高优先级待确认项闭环 |
| 2 | `review-requirements` | 完善后的需求 | 漏洞清单、澄清清单、门禁结论 | 无未解决"高"级问题 |
| 3 | `split-requirements` | 评审通过的需求 | 功能拆分总表、AC 清单、验收口径 | 高优先级待确认项闭环 |
| 4 | `design-testcases` | 拆分总表、AC 清单 | 用例清单 YAML + Excel、覆盖矩阵 | 每个 AC 至少一条用例 |
| 5 | `review-testcases` | 用例清单、覆盖矩阵 | 多视角评审纪要 | 无"高"级问题 |
| 6 | `test-script` | 评审通过的用例 | `api_clients/`、`tests/api/`、`data/` 代码 | 自检清单全部通过 |
| 7 | `code-review` | 脚本 diff | 评审纪要、合并门禁 | 无"高"级问题 |
| 8 | `run-tests` | 评审通过的脚本、执行范围 | 执行报告、失败归因 | 无 failed/error 且非全部 skip |
| 9 | `test-report` | junit、用例清单、git 信息 | 含用例明细的完整报告 | 数字与 junit 一致、每个失败有归因 |
| 10 | `bug-analysis` | 失败用例、请求响应、日志 | 缺陷单、根因分析 | 已排除环境/数据/脚本归因 |

## 执行规则
1. **一次只推进一个阶段**：完成当前阶段产出后再进入下一步，不跳步、不并行改写。
2. **门禁即停止点**：门禁不通过时停止流程，输出阻断原因与需要谁补齐什么，不擅自降低标准放行。
3. **待确认项全程追踪**：每个阶段新增的【待确认】项合并到同一张清单，编号 `Q-{序号}` 不重复。
4. **用户要求跳步时**：说明跳过阶段带来的风险（如缺 AC 会导致用例无法追溯），用户确认后再继续，并在最终产物中标注"未评审"。
5. **产物落位固定**：
   - 需求 / 拆分结果：`requirements/`
   - 用例清单：`testcases/REQ-{需求号}-TC-list.yaml` 与同名 `.xlsx`
   - 脚本：`tests/api/`、`api_clients/`、`data/`
   - 报告：`reports/`（junit.xml 与执行报告）

## 阶段交接模板
每次阶段完成，输出：

```
【阶段】{步骤号} {skill 名}
【产出】{产物路径 / 章节}
【门禁】通过 / 有条件通过 / 拒绝
【未闭环】{待确认项编号与责任方}
【下一步】{下一个 skill，或需用户确认的事项}
```

## 快速开始
1. 判断用户输入处于哪一步：只有原始文档 → 从步骤 1 开始；已有拆分表 → 从步骤 4 开始；已有用例 → 从步骤 5 开始；已有脚本 → 步骤 7 评审，再步骤 8 执行；只验证现有脚本 → 直接步骤 8；需要带明细的报告 → 步骤 9；出现真实失败需提缺陷 → 步骤 10。
2. 明确告知从哪一步开始、为什么。
3. 按对应 Skill 的规则执行，不在本 Skill 里重复各阶段的细则。

## 输出禁忌
- 禁止跳过门禁直接产出下游文件。
- 禁止在本 Skill 中重复输出用例、脚本等阶段细节。
- 禁止丢失前序阶段的待确认项。
- 禁止在用户未确认时自行认定"有条件通过"等于"通过"。
