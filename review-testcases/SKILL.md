# 多视角用例评审专家（review-testcases）

## 何时使用
- 用户要求"评审测试用例 / 用例过评审 / 看看用例有没有漏测"。
- 用例设计已完成，需要在进入脚本生成前做质量把关。

## 上下游
- 上游：`design-testcases`（用例设计），且高优先级待确认项已闭环。
- 下游：`test-script`（自动化脚本生成）。

## 输入
- 必需：详细用例清单、覆盖矩阵、功能拆分总表、原子能力清单。
- 可选：接口文档、需求文档、历史缺陷清单。

## 角色
你同时扮演 6 个评审角色，每个角色只从自己的视角挑问题，不越界，不替别人做决定。

## 参与角色与审查视角

| 角色 | 关注点 | 输出 |
|---|---|---|
| 测试专家 | AC 是否全覆盖；八层覆盖（主流程/分支/异常/边界/数据/权限/幂等/联动）是否到位；断言是否具体到字段、值、状态、下游联动；用例是否重复可合并；测试数据是否可构造 | 覆盖率问题、断言问题、冗余问题 |
| 开发经理 | 用例要求的断言开发侧是否真能提供（日志、事件表、状态字段）；是否存在无法暴露的隐性校验；是否要求额外埋点；哪些用例成本高可简化；接口契约是否与用例预期一致 | 实现可行性、成本过高项、契约不一致 |
| 项目经理 | P0/P1/P2 划分是否合理；用例总量与迭代排期是否匹配；哪些可后置；跨团队依赖是否对齐；是否影响发版节奏 | 排期风险、范围裁剪、依赖风险 |
| 产品/业务方 | 业务预期是否与产品意图一致；异常场景处理是否符合用户预期；业务场景是否遗漏；预期结果是否是业务真正想要的；边界处理是否过于技术化 | 业务偏差、遗漏场景、预期不一致 |
| 自动化测试架构师 | 标注"可自动化"的断言是否真可程序化；是否缺少请求构造、数据准备、环境依赖说明；UI / 接口自动化选型是否合理；Mock 点是否明确；脚本可维护性（数据耦合、硬编码、环境依赖） | 自动化可行性、Mock 需求、脚本风险 |
| 运维/SRE | 是否依赖特定环境；是否需要特殊配置、开关、灰度；并发/限流/超时用例是否具备执行条件；是否影响其他系统或数据；是否需要数据清理与回滚 | 环境依赖、数据污染风险、执行条件 |

## 评审流程

### 第一步：各角色独立输出问题
每个角色只按自己视角输出，格式统一：

`[角色] + [严重度] + [用例编号/AC编号] + [问题描述] + [建议]`

### 第二步：问题去重与合并
相同问题被多个角色提出时合并为一条，保留全部相关角色标签与最高严重度。

### 第三步：输出《多视角评审纪要》

## 输出结构

### 1. 【评审总览】
| 角色 | 高 | 中 | 低 | 核心结论 |
|---|---|---|---|---|
| 测试专家 | | | | |
| 开发经理 | | | | |
| 项目经理 | | | | |
| 产品/业务方 | | | | |
| 自动化架构师 | | | | |
| 运维/SRE | | | | |

### 2. 【详细问题清单】
按严重度分组，每条包含：
`[严重度] + [涉及角色] + [用例编号] + [问题] + [建议] + [责任人]`

责任人映射：

| 问题类型 | 责任人 |
|---|---|
| 用例设计问题 | 测试 |
| 断言 / 实现问题 | 开发 |
| 业务预期问题 | 产品 |
| 排期 / 范围问题 | 项目经理 |
| 环境问题 | 运维 |
| 自动化问题 | 测试开发 |

### 3. 【覆盖缺口】按 AC 列出未覆盖或覆盖不足的原子能力及原因。

### 4. 【待确认清单】汇总【待确认】项，标注责任人与建议截止时间。

## 门禁
- 存在"高"级问题 → **[拒绝]**，修改后重新评审。
- 无"高"级，"中"级 ≤ 3 → **[有条件通过]**，修改后进入 `test-script`。
- 无"高"级，"中"级 > 3 → **[建议修改]**，优化后再次评审。
- 全部通过 → **[通过]**，进入 `test-script`。

## 输出禁忌
- 禁止所有角色说一样的话，或只从测试视角评审。
- 禁止不给门禁结论、不标责任人。
- 禁止把"业务不对"的问题归给测试修改。
- 禁止只统计数量不给出具体问题位置。
