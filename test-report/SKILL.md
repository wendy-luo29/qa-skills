# 测试报告生成（test-report）

## 何时使用
- `run-tests` 执行完成，需要一份可交付、可追溯的报告。
- 现有报告只有汇总数字，缺少用例明细、失败证据或覆盖分析。
- 需要推送到飞书群、归档到 `reports/` 或附在发布单中。

不适用：执行用例 → `run-tests`；分析失败根因并修脚本 → `test-script`。

## 上下游
- 上游：`run-tests`（提供 junit、失败证据、环境信息）。
- 下游：发布门禁、缺陷单、周报。

## 数据源（缺一项就在报告里标注"缺失"，不要编造）

| 数据 | 来源 | 用途 |
|---|---|---|
| 用例执行结果 | `reports/junit.xml` | 每条用例的结果、耗时、失败信息 |
| 失败证据 | pytest 输出、`reports/report.html`、`logs/`、`.screenshots/` | 失败分析与复现 |
| 用例元数据 | `testcases/REQ-xxx-TC-list.yaml` | 标题、AC、优先级 |
| AC 清单 | 拆分结果中的 `AC-xx` | 覆盖率分母 |
| 代码版本 | `git rev-parse --short HEAD`、`git branch --show-current` | 可追溯 |
| 环境 | `config/env.yaml` 的 `api_base_url` | 区分环境 |

## 报告结构（按顺序输出，不得缺项）

### 1. 报告头
标题、需求号、环境 URL、分支、commit、执行方式（本地 / CI）、执行时间、执行范围（marker / 路径）。

### 2. 结论摘要
```
总计 51 ｜ 通过 35 ｜ 失败 3 ｜ 跳过 11 ｜ XPASS 2 ｜ 耗时 2.12s
有效执行率 78.4%（skip 不计入通过）｜ 非跳过通过率 87.5%
结论：不通过（3 条真实缺陷待修复）
```

### 3. 模块统计
| 模块 / 文件 | 选中 | 通过 | 失败 | 跳过 | 耗时 | 通过率(非跳过) |

### 4. 用例明细（报告的核心，不能省略）
全部用例逐条列出：

| 用例编号 | 用例标题 | 关联 AC | 优先级 | 结果 | 耗时 | 备注 |

- 结果取值：PASS / FAIL / SKIP / XPASS / XFAIL。
- 备注写失败摘要或跳过原因，不写"见上"。
- 超过 100 条时：正文列"全部失败 + 全部 P0 + 全部 SKIP"，其余按模块折叠或放 HTML 附件，但总数必须与 junit 一致。

### 5. 失败明细（每条失败一个区块）
```markdown
### TC-ADDR-009 test_null_or_empty_key_fields
- 关联 AC：AC-02
- 现象：期望 code=400 / data=null / wrapper.success=false，实际 code=200
- 请求：POST /address/validate  {"address": "", ...}
- 响应：{"code": 200, "data": {...}}
- 归因：E 真实缺陷（空地址被当作合法地址校验通过）
- 证据：reports/report.html#TC-ADDR-009、logs/api-20261117.log:120
- 建议：交后端确认空地址校验分支
```

归因只能取：A 环境 / B 数据 / C 脚本缺陷 / D 需求预期不一致 / E 真实缺陷。需要正式提交的缺陷单转 `bug-analysis`，其中必须含地址、请求参数、返回结果和关联用例。

### 6. 跳过明细
| 用例编号 | 跳过原因 | 影响判断（可补测 / 环境限制 / 预期） |

### 7. 覆盖分析
```
AC 总数：3 ｜ 已覆盖：3 ｜ 覆盖率 100%
P0 覆盖率：100%（6/6）｜ P1 覆盖率：80%（8/10）
未覆盖 AC：AC-07（无用例，需补）
```

### 8. 风险与待确认
列出执行中发现的待确认项（`Q-xx`）、环境限制、数据依赖，以及它们对结论的影响。

### 9. 结论与下一步
- 结论：通过 / 有条件通过（仅 A 类失败或环境限制）/ 不通过
- 下一步：提缺陷 / 补用例 / 修脚本 / 可发布
- 明确"本次未验证的内容"，避免把 skip 当通过。

## 生成流程

1. 收集数据：确认 `reports/junit.xml` 与用例清单存在；缺失时先补生成，不用单次控制台输出替代。
2. 关联 `case_id`：junit 的 `name` → 用例清单的 `case_id`；关联不上要单列"未登记用例"，不能静默丢弃。
3. 计算指标（公式见下），统一保留一位小数。
4. 先输出 Markdown 全文，再按渠道裁剪：飞书只发摘要 + 失败 Top5 + 报告链接；明细放 HTML 附件或链接。
5. 落盘到 `reports/REQ-{需求号}-test-report-{yyyyMMdd-HHmm}.md`，与 `junit.xml`、`report.html` 同目录。

## 指标口径（必须统一，禁止自定义）

| 指标 | 公式 |
|---|---|
| 有效执行率 | (passed + failed) / total |
| 非跳过通过率 | passed / (passed + failed) |
| AC 覆盖率 | 有用例执行的 AC 数 / AC 总数 |
| 失败率 | failed / (passed + failed) |
| XPASS | 计入通过数展示，但必须单独标注 |

## 推送（必须执行，不推送不算交付）

生成报告后立即推送，不能只把 Markdown 输出到对话里：

```bash
python scripts/send_report.py
```

- 默认推送 `reports/report.html`（--report 可覆盖）与 `reports/bugs/*.xlsx`（--bug-xlsx 可指定单个）。
- 缺陷 Excel 必须先由 `bug-analysis` 生成，再执行推送；目录为空时消息会标注"无"。
- 本地凭证从 `D:\ai-test-framework\.env` 读取（已 gitignore），CI 从 `FEISHU_WEBHOOK` Secret 读取。
- 群自定义机器人 webhook 不支持附件，消息以 post 富文本推送，报告与缺陷 Excel 均为可点击超链接。
- 链接优先用 `--report-url`（CI artifact），本地回退 `file:///` 绝对路径，仅本机可打开；需要全员可访问时改用 Open API 应用凭证上传附件。
- 脚本输出"已发送飞书通知"才算完成；只生成了文件、没执行推送，视为未完成。
- 推送失败时保留报错信息，不得在报告中写"已通知"。

## 飞书推送规范
- 摘要不超过 20 行：环境、接口地址、分支、结果、两个通过率、失败 Top5（带 case_id）、测试报告链接、缺陷明细链接。
- 明细不发文本长消息，改为超链接到 HTML / Excel。
- 禁止在群消息里省略失败数量或用"基本通过"等模糊表述。

## 门禁
- 报告数字与 junit 完全一致，总数能对上。
- 每个 FAIL 都有归因与证据，不允许只有 traceback。
- 存在未覆盖的 P0 AC 时，结论不得为"通过"。
- 全部 skip 时结论必须是"未执行/阻断"，不能写"通过"。
- 必须已执行推送并收到"已发送飞书通知"，否则报告未交付。

## 输出禁忌
- 禁止只给汇总数字、不给用例明细。
- 禁止把 skip / xfail 算作通过。
- 禁止编造耗时、覆盖率、证据路径。
- 禁止在报告中泄露密码、token、webhook 等凭证。
- 禁止与 `run-tests` 的归因结论冲突而不说明修订原因。
